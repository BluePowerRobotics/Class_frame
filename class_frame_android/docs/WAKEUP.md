# 双通道设备上的唤醒与自启动

## 背景

希沃这类机器把 Windows 的画面交给 Android 侧显示（Android 掌握显示通道），
所以 **Android 一定在运行**，不存在"Android 没起来"。

出问题的是两件事：

- Android 侧可能在 Windows 通道激活期间被冻结（厂商为省电冻结非前台通道）；
- 厂商可能不给第三方应用自启动机会，`BOOT_COMPLETED` 被推迟到切通道那一刻。

表现就是"开机后切到 Android 通道，悬浮层才出现"。

## 我们用的唤醒链路

| 触发点 | 作用 |
| --- | --- |
| `BOOT_COMPLETED` | 正常开机自启（需开启"启用开机自启"） |
| `QUICKBOOT_POWERON` | 部分厂商的快速启动动作 |
| `MY_PACKAGE_REPLACED` | 覆盖安装后自启，避免"装了却没反应" |
| `USER_PRESENT` | 解锁后补一次（30 秒去抖） |
| 主闹钟 | 到点显示 / 到点隐藏 |
| **课前自检闹钟** | 首节课前 N 分钟强制醒一次并重新排定（见下） |
| 1Hz 心跳 | 进程存活时每秒对齐秒边界，每 30 秒重核调度 |
| `ensureOverlayAlive` | "该显示但窗口没挂上"时限频重试 |

## 课前自检闹钟

为什么需要它：主闹钟负责"到点显示"，但如果 Android 侧在那一刻被冻结、
或厂商拦掉了闹钟，整个唤醒就丢了。自检闹钟在**首节课开始前 N 分钟**
（system 页可设，默认 1 分钟，0 表示关闭）再醒一次，重新算一遍状态。

关键点：

- 它**不决定显示或隐藏**，只负责重新评估。显示/隐藏仍由状态机决定，
  所以不会出现"自检把自己唤醒了就强行显示"的情况。
- 它按**校正后的时间**计算，再换算回设备时钟排给 `AlarmManager`。
  改过时间偏移后 `applySchedule` 会重排，因此偏移校正后的"残余"不会留在闹钟里。
- 自检点若早于"显示"时刻（课前 1 小时），会顺延到显示时刻之后，避免重复触发。
- 自检时刻永远排在未来 60 秒之后，不会因为"已经过点"而被立刻反复触发。

## 精确闹钟

`setExactAndAllowWhileIdle` 在 Doze 下也能唤醒 CPU 投递广播，屏幕不必点亮。
前提：

- Android 12+ 需要"闹钟与提醒"（`SCHEDULE_EXACT_ALARM`）权限；拿不到时降级为
  `setAndAllowWhileIdle`，触发可能偏移几分钟到十几分钟。
- **厂商允许**。如果希沃在 Windows 通道期间冻结了 Android 侧的闹钟投递，
  任何软件手段都无法在该时刻唤醒——只能在它醒来的第一个瞬间把状态补正。

## 怎么验证

日志是唯一证据，全部写在 `/存储/下载/ClassFrame/class_frame.log`：

```
BootReceiver 收到 android.intent.action.BOOT_COMPLETED
service onCreate
闹钟已排: 09-24 07:00:00 距现在 43200 秒
闹钟已排（课前自检）: 09-24 07:59:00 距现在 46740 秒
```

判断方法：

- 该响的时刻只有 `app 启动` 而没有 `ScheduleReceiver 闹钟触发`——闹钟被 ROM 拦了。
- 有 `闹钟触发` 却没有 `overlay show ok`——窗口挂载被拒，看同段异常栈。
- 一整段日志的时间戳对应"切通道"那一刻——说明 Android 侧此前被冻结。
